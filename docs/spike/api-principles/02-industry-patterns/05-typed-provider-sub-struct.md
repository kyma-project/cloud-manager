# Pattern 5: Typed Provider Sub-Struct

When the resource envelope is shared (lifecycle, status contract, common references) but some configuration is genuinely provider-specific, a typed `spec.instance.<provider>` sub-struct keeps the resource tidy — users only see fields relevant to their provider — while CRD-level `MaxProperties=1` enforces exactly one sub-struct is set.

---

## Where This Pattern Comes From

### Crossplane Composite Resources + Managed Resources
**Repo:** [crossplane/crossplane](https://github.com/crossplane/crossplane)
**Key file:** [`apis/apiextensions/v1/composition_types.go`](https://github.com/crossplane/crossplane/blob/master/apis/apiextensions/v1/composition_types.go)

A neutral Claim carries shared fields. A Composition maps Claim fields to provider-specific Managed Resource fields. The provider-specific fields live in `spec.forProvider` — a typed sub-struct per provider implementation.

```yaml
# User writes (Claim — neutral envelope):
kind: XPostgreSQLInstance
spec:
  parameters:
    storageGB: 20
    version: "14"
    tier: standard          # neutral concept

# AWS Managed Resource (generated by Composition, not user-facing):
kind: RDSInstance
spec:
  forProvider:              # typed provider sub-struct
    dbInstanceClass: db.t3.small   # mapped from tier=standard
    engineVersion: "14.9"          # mapped from version="14"
    allocatedStorage: 20
```

**Lesson for CM:** The `forProvider` sub-struct pattern is exactly what CM's KCP layer does with `spec.instance.gcp`, `spec.instance.aws`, etc. The SKR layer should apply the same discipline to field *naming* — not structure — so users learn one field name regardless of which provider sub-struct they're in.

### Cluster API — Infrastructure Provider Contract
**Repo:** [kubernetes-sigs/cluster-api](https://github.com/kubernetes-sigs/cluster-api)
**Key file:** [`api/v1beta1/cluster_types.go`](https://github.com/kubernetes-sigs/cluster-api/blob/main/api/v1beta1/cluster_types.go)

`Cluster` holds provider-agnostic fields. The `spec.infrastructureRef` points to a typed provider object (`AWSCluster`, `GCPCluster`). The provider object has its own typed spec — there is no union, no `map[string]interface{}`.

```yaml
kind: AWSCluster              # typed — not unstructured
spec:
  region: "us-east-1"
  network:
    vpc:
      cidrBlock: "10.0.0.0/16"

status:
  ready: true                 # contract field — same name on all provider objects
```

**Lesson for CM:** Typed sub-structs give the CRD schema full validation power per provider. The contract (what fields the sub-struct must populate in status) is what makes the base resource portable.

## How Cloud Manager Uses This Pattern

**KCP RedisInstance — already correct:**

```yaml
kind: RedisInstance           # cloud-control API group
spec:
  scope:
    name: my-scope            # base — same on all providers
  ipRange:
    name: my-iprange          # base — same on all providers
  instance:                   # exactly one sub-struct (MaxProperties=1)
    gcp:
      memorySizeGb: 6
      tier: "STANDARD_HA"
      redisVersion: "REDIS_7_0"
    # aws: / azure: / alicloud: are mutually exclusive

status:
  memorySizeGb: 6             # normalized output — same field on all providers
  primaryEndpoint: "10.0.0.5:6379"
```

No change needed at the KCP layer.

## Applying to CM CRD Families

### Redis — config map field naming at SKR layer

The config map concept is the same on all providers — freeform Redis configuration key-value pairs. The field *name* should be consistent across SKR resources. Having `parameters`, `redisConfigs`, and `redisConfiguration` for the same concept forces users to re-learn the name per provider.

**Before:**
```yaml
kind: AwsRedisInstance
spec:
  parameters:                       # freeform map[string]string
    maxmemory-policy: volatile-lru

---
kind: GcpRedisInstance
spec:
  redisConfigs:                     # same concept, different name
    maxmemory-policy: volatile-lru

---
kind: AzureRedisInstance
spec:
  redisConfiguration:               # same concept, different name, typed struct
    maxmemory-policy: "volatile-lru"
    maxclients: "8"
```

**After:**
```yaml
kind: AwsRedisInstance
spec:
  parameters:                       # unchanged
    maxmemory-policy: volatile-lru

---
kind: GcpRedisInstance
spec:
  parameters:                       # was: redisConfigs
    maxmemory-policy: volatile-lru

---
kind: AzureRedisInstance
spec:
  parameters:                       # was: redisConfiguration
    maxmemory-policy: "volatile-lru"
    maxclients: "8"
    # Azure's typed field set is preserved in the controller validation —
    # only the CRD field name changes
```
