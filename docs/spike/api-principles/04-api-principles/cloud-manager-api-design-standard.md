# Cloud Manager API Design Standard

> **Status:** Active | **Version:** 1.0

---

Cloud Manager aims to reduce the friction of consuming cloud-managed services from Kyma, improving usability and reducing the amount of knowledge required to create and manage cloud resources regardless of the underlying provider.

This standard defines how that experience is designed and implemented. It applies to every Cloud Manager feature going forward. The core idea is simple: resources are defined once and work everywhere, but users who need to go deeper always have a path to do so. The layers described below are not stages users must pass through — they represent how far a user can go if they need to.

---

## 1. Design Premises

These premises define the direction. Every Cloud Manager feature must follow all three.

| # | Premise | What it means |
|---|---|---|
| P1 | **Same object across clouds** | One YAML works on AWS, GCP, and Azure without changes |
| P2 | **No cloud knowledge required** | A user with Kubernetes experience can deploy without reading cloud provider documentation |
| P3 | **Provider-specific configuration can be configured as required** | When users need fine-grained control, a typed and documented path exists to configure it |

---

## 2. The Four-Layer Model

Cloud Manager features are structured around four layers. The layers represent depth of configuration — from the minimum information Cloud Manager needs to work, to full provider-specific control. Not every feature exposes all four layers; Layer 3 may be its own dedicated CRD that exists only when necessary.

| Layer | Name | Purpose |
|---|---|---|
| 0 | Auto-Detection | Cloud provider is resolved automatically from Kyma Scope |
| 1 | Minimal Declaration | The information Cloud Manager truly needs and cannot work without |
| 2 | Neutral Tuning | Customisable options with defaults that allow users to further configure the feature |
| 3 | Provider-Specific Config | Allowing users to further customise objects using provider-specific configuration |

Layer 3 (provider-specific configuration) is generated by Cloud Manager from lower-layer toggles when absent.

This model implements the common approaches observed in the field **01 — Common Base with Provider-Specific Extensions**, **02 — Neutral Intent Resource**, and **03 — Consistent Field Naming**, while also aiming to achieve **06 — Portable Container with Unstructured Payload** at Layer 2.

## 3. CRD Design Rules

### Field naming

| Rule | Correct | Avoid |
|---|---|---|
| Neutral field names | `memorySizeGb`, `tier`, `engineVersion` | `skuName`, `cacheParameterGroup`, `diskType` |
| Neutral enum values | `tier: standard` | `tier: Standard_LRS` |
| No provider prefixes in neutral fields | `spec.backend` | `spec.gcpBackend` |
| Provider sub-structs for Layer 3 | `spec.aws`, `spec.gcp`, `spec.azure` | `spec.providerConfig: {}` |
| Kind names should not encode the provider when possible | `WafPolicy` | `AzureWafPolicy` |

### Spec structure

```yaml
spec:
  # Layer 1: the information required from the user

  # Layer 2: optional neutral tuning — Cloud Manager applies managed defaults
  # for anything not set here. Defaults are transparent (see status).
  # <featureOption>: true | false
  # <neutralParam>: <value>

  # Layer 3: provider-specific configuration — the provider-native trump card.
  # Optional. When absent, Cloud Manager generates it from Layer 2 settings.
  # When provided, it is used verbatim. The user takes full responsibility for
  # maintaining it and will not automatically benefit from default improvements.
  # Example: WafPolicy generates a Cloud Armor / WAF Web ACL policy from the
  # Layer 2 toggles above; a user who needs full control can supply the raw
  # provider configuration here instead.
```

### Managed Defaults

Cloud Manager provides managed defaults for all Layer 2 fields, based on current best practices and operational experience. They are maintained by the Cloud Manager team and updated as cloud providers evolve — users automatically benefit from improvements without changing their configuration.

Defaults must not be hidden in controller code. Every resource must surface in its status where each applied value came from: whether it was set explicitly by the user, applied from a managed default, or assigned by the platform during fulfillment. This makes defaults inspectable by humans and AI tooling, so the real reason a resource behaves a certain way can always be traced.

When a user overrides a default via Layer 3, they take ownership of that configuration. It will not automatically receive updates from the Cloud Manager team. This is a deliberate trade-off and should be a conscious choice, not the path of least resistance.

### Versioning

All features start at `v1beta1`. Resources are production-intended; `v1alpha1` signals instability.

### Status

Every CRD must expose this status structure:

```yaml
status:
  state: Creating | Ready | Updating | Deleting | Error
  observedGeneration: <int64>
  conditions:
    - type: Ready
      status: "True" | "False" | "Unknown"
      reason: <CamelCase>
      message: <human-readable string>
      lastTransitionTime: <RFC3339>
  # Feature-specific fields (e.g. providerId, endpoint, url)
```

**Condition reason vocabulary:**

| Reason | When to use |
|---|---|
| `Reconciled` | Resource successfully created or updated |
| `ProvisioningFailed` | Cloud API returned an error during create or update |
| `DeletionFailed` | Cloud API returned an error during delete |
| `MissingDependency` | A referenced resource (e.g. a policy, a network) does not exist yet |

## 4. References and Prior Art

The following resources were studied to reach this design. They are listed here so future contributors understand the foundation and can revisit the original thinking when evolving the standard.

**Common approaches observed in the field:**

| # | Pattern | Description |
|---|---|---|
| 01 | Common Base with Provider-Specific Extensions | Shared user intent in a provider-agnostic base; provider-specific configuration in typed extensions referenced from that base |
| 02 | Neutral Intent Resource | User expresses what they need using provider-agnostic concepts; the controller routes to the correct provider at runtime |
| 03 | Consistent Field Naming | When the same concept exists across all providers, the field name is identical everywhere; value-format differences are mapped by the controller |
| 04 | Provider-Specific Resource | When cloud concepts differ structurally across providers, a dedicated resource per provider avoids a union-type CRD |
| 05 | Typed Provider Sub-Struct | A typed `spec.<provider>` sub-struct with mutual exclusion keeps provider-specific configuration fully validated within a shared envelope |
| 06 | Portable Container with Unstructured Payload | When the provider-native payload has no meaningful cross-provider schema, CM owns the typed envelope while the payload is passed through for the cloud provider to validate |

**Industry tools studied:**

- **Crossplane v2** (CNCF Graduated) — XRD + Composition model separates the API contract from implementation; continuous cloud reconciliation. *Taken:* the principle that the user-facing schema is pure intent and the controller does the translation. *Left:* the need for users to choose a `compositionSelector` or know which Composition to use.

- **kro** (alpha, co-maintained by AWS, Azure, Google) — one `ResourceGraphDefinition` per cloud, auto-inferred resource dependency ordering via CEL expressions. *Taken:* the instinct to keep genuinely different things separate. *Left:* the one-RGD-per-cloud model that gives each cloud a different Kind — the opposite of Cloud Manager's goal.

- **Kratix** — Promise model wrapping any tooling; first-class multi-cluster routing via Destinations. *Taken:* the single Kind across clouds achieved through a pipeline translation layer. *Left:* the imperative pipeline container execution model.

- **Gardener `DNSEntry`** — provider omitted from spec entirely; controller routes to Route53, Cloud DNS, or Azure DNS from cluster context.

- **Kubernetes `Service.type: LoadBalancer`** — cloud-neutral Kind that works on every provider unchanged.

- **Kubernetes `PersistentVolumeClaim` + `StorageClass`** — user declares intent; provider details live in a separate object.

- **ACK / KCC / ASO** — negative reference: encoding the provider in the Kind prevents reuse across clouds.
